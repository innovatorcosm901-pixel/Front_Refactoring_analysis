Краткое резюме

TanStack Start — надстройка над текущим стеком

Start построен поверх того же @tanstack/react-router, который уже импортируют 205 файлов проекта. Роутинг, файлы маршрутов, хлебные крошки на useMatches(), Link/useNavigate/useParams в 73 файлах — всё продолжает работать без правок. Vite и Tailwind v4 через @tailwindcss/vite тоже остаются.

Отсюда объём работ на 28% меньше (13–18 дней разницы) и меньшая доля затронутых файлов на кодовой базе без единого автотеста. Внедрение инкрементально: приложение сначала едет в режиме defaultSsr: false, где рантайм-поведение в браузере не меняется вообще, а SSR включается маршрут за маршрутом с откатом в одну строку.

Обратная сторона — отсутствие RSC (весь код страниц едет в браузер), меньшая экосистема и подвижный API внутри линейки 1.x.

Next.js — замена текущего стека

Next даёт то, чего у Start нет: React Server Components как рычаг сокращения бандла, next/image, Server Actions, десятилетнюю экосистему, Active LTS до 2027 года и обширную документацию. Защита маршрутов через middleware.ts существует по построению, а не собирается вручную.

Объём работ при этом — 46–66 дней. Полностью заменяется роутер (205 файлов), переписываются все 132 файла маршрутов, теряется типобезопасность ссылок, нужен собственный реестр хлебных крошек взамен useMatches, и на 371+ файле страниц расставляются границы "use client".

При нулевом тестовом покрытии это определяет профиль риска: правится 60–80% файлов, а проверять результат нечем, кроме ручного чек-листа.

Что даёт каждый фреймворк

Ключевые технические возможности «из коробки» и их отношение к потребностям ict_front.

TanStack Start

  • Сохранение существующего роутинга Все 132 маршрута, staticData.breadcrumb, useNavigate, useParams, <Link> продолжают работать без изменений. Это главный источник экономии времени и снижения риска регрессий.
  • Vite как сборщик Быстрая разработка (HMR), знакомый конфиг, отсутствие необходимости переучиваться на Turbopack/Webpack.
  • Инкрементальный SSR Возможность начать с SPA-режима на Node (defaultSsr: false), затем включать SSR для отдельных маршрутов (data-only → true). Это позволяет выкатывать изменения постепенно, минимизируя риски.
  • Серверные функции (createServerFn) RPC-подход с полной типобезопасностью, валидацией через Zod (уже есть в проекте), поддержкой middleware — как на клиенте, так и на сервере.
  • Единый слой данных с TanStack Query Нативная интеграция с setupRouterSsrQueryIntegration, автоматическая гидратация кэша, loader-ы с ensureQueryData. Нет необходимости вручную оборачивать страницы в HydrationBoundary.
  • Типобезопасность на всех уровнях От маршрутов до серверных функций — что существенно для ERP-системы с множеством бизнес-сущностей.
  • Гибкость деплоя Приложение разворачивается на любом Node-хостинге, без привязки к конкретному провайдеру. Управление инфраструктурой полностью остаётся в руках команды.

Next.js (App Router)

  • React Server Components (RSC) Позволяет сократить клиентский бандл, перемещая тяжёлую логику рендеринга на сервер. Даёт снижение размера JavaScript и улучшение TTI на сложных дашбордах.
  • Встроенные оптимизации next/image для автоматической оптимизации изображений, next/font для шрифтов, автоматический код-сплиттинг на уровне страниц.
  • Зрелая экосистема и сообщество Огромное количество готовых решений, библиотек и примеров. Любая проблема уже кем-то решена и документирована.
  • Стабильный и предсказуемый API Фреймворк развивается 10+ лет, обратная совместимость на высоком уровне, критические изменения выходят с длительным предупреждением.
  • Глубокая интеграция с Vercel Если в будущем появится желание перейти на облачную платформу, Vercel предоставит максимально удобный опыт: автоматические деплои, аналитика, Edge-функции.
  • Server Actions Встроенный механизм для выполнения серверного кода из клиентских компонентов, с автоматической защитой от CSRF и шифрованием данных.
  • ISR и PPR (Partial Prerendering) Позволяют комбинировать статическую и динамическую генерацию — что может быть полезно для публичных страниц, если они появятся.

Технические модели: чем отличается устройство

Три места, где фреймворки расходятся не количественно, а концептуально. Веса в таблице выше отражают приоритеты именно этого проекта — при других приоритетах итоговые баллы изменятся.

Подход к SSR

Next.js

Server Components по умолчанию: каждый компонент считается серверным, пока не помечен явно. Клиентские компоненты выделяются директивой "use client", и границу нужно провести осознанно по всему дереву — для ict_front это 371+ файл страниц.

Модель мощная, но переключателя «сделать всё как раньше» в ней нет: приложение сразу живёт в серверной парадигме.

TanStack Start

Интерактивные компоненты по умолчанию, SSR включается опционально — на уровне маршрута и в трёх состояниях: false, data-only (на сервере выполняется только загрузка данных) и true (полный серверный рендер разметки).

Это даёт больше контроля и постепенности: можно приехать на сервер, ничего не меняя в поведении браузера, и включать SSR маршрут за маршрутом.

Модель кеширования

Next.js

Многоуровневый кеш: потоки RSC, кеш fetch, кеш роутера на клиенте, плюс полностраничный кеш. Уровни взаимодействуют между собой, а инвалидация выполняется через revalidatePath/revalidateTag.

Сильная сторона — при верной настройке кеш работает без участия прикладного кода. Слабая — модель требовательна к настройке, и в мультиинстансном self-hosted-деплое нужен собственный cacheHandler.

TanStack Start

Явный SWR-подход: кеш живёт в роутере (loader) и в TanStack Query. Никакого скрытого слоя между ними нет — что закешировано, видно из кода.

staleTime и gcTime уже знакомы команде: React Query используется в проекте сегодня — 121 useQuery и 113 useMutation. Переучиваться на новую модель кеширования не требуется.

Серверные операции

Server Actions (Next.js)

Интеграция с формами из коробки: функция передаётся в <form action> и работает даже до гидратации. Есть автоматическая защита от CSRF и шифрование замыканий, передаваемых с сервера на клиент.

Технически каждое действие — публичный POST-эндпоинт, поэтому авторизацию и валидацию входа нужно писать внутри самого действия: вызвать его может кто угодно.

Server Functions (TanStack Start)

RPC-стиль: createServerFn с явным методом (GET или POST), валидатором входа (inputValidator + Zod, уже используется в 18 файлах проекта) и цепочкой middleware — общей для клиента и сервера.

Типы входа и выхода выводятся сквозь всю цепочку, поэтому граница клиент/сервер проверяется компилятором. Готовой интеграции с формами уровня Server Actions при этом нет.

Риски и ограничения

Что может пойти не так в каждом из вариантов — включая риск повторного рефакторинга и технические ограничения, проявляющиеся уже после выкатки.

При выборе TanStack Start

  • Молодость фреймворка Первый стабильный релиз (v1.0) вышел в марте 2026 года. Некоторые крайние случаи использования ещё не проверены в бою, а API внутри линейки 1.x может меняться — уже были переименования @tanstack/start → @tanstack/react-start и .validator() → .inputValidator(). Риск нарваться на баг, который ещё не исправлен, выше, чем у Next.js.
  • Отсутствие RSC в production На данный момент поддержка React Server Components экспериментальная. Если в будущем потребуется массовое использование RSC для сокращения бандла, Start может не успеть за потребностями.
  • Меньшее сообщество и меньше готовых решений При возникновении нестандартной задачи — например, интеграции с корпоративной системой логирования или сложного self-hosted-деплоя — придётся разбираться самостоятельно, опираясь на исходники и ограниченную документацию.
  • Риск «застрять» на версии Если команда не будет активно следить за обновлениями, можно остаться на версии с критическим багом. Лечится фиксацией точной версии (--save-exact) и регулярным аудитом changelog.
  • Производственные ошибки Как любой молодой фреймворк, Start может содержать ошибки, которые в Next.js уже исправлены за счёт многолетней эксплуатации. Примеры из issue-трекера: проблемы с деплоем на Cloudflare Workers (падение production-сборки), ошибки с получением токена аутентификации на сервере, неочевидное поведение middleware.

При выборе Next.js

  • Колоссальный объём миграции Требуется переписать 132 маршрута, 205 файлов, использующих TanStack Router, и адаптировать 371 файл страниц под модель Server Components — расстановка "use client". При нулевом тестовом покрытии это создаёт значительный риск функциональных регрессий.
  • Сложность self-hosting Next.js официально поддерживает деплой на собственные сервера, но это требует настройки дополнительных компонентов: cacheHandler для мультиинстансности, NEXT_SERVER_ACTIONS_ENCRYPTION_KEY, deploymentId, явного отключения буферизации nginx для стриминга. Каждый из этих шагов может стать источником ошибок в проде.
  • «Двойная» модель данных При одновременном использовании RSC и React Query возникают два конкурирующих слоя данных: fetch в RSC и useQuery на клиенте. Для команды без опыта SSR это частая причина ошибок гидратации и неконсистентности данных.
  • Потеря существующей типобезопасности TanStack Router даёт полную типизацию маршрутов, search-параметров и ссылок. В Next.js typedRoutes восстанавливает часть этой безопасности, но она менее глубокая и требует дополнительных усилий.
  • Риск «переписать и не закончить» Из-за большого объёма и отсутствия автотестов миграция может затянуться на многие месяцы, и проект рискует остаться в гибридном состоянии: часть страниц на старом стеке, часть на новом. Это увеличивает сложность разработки и поддержки.

Как это читается

Start добавляет сервер к тому, что уже есть; Next заменяет то, что уже есть. При нулевом тестовом покрытии это и есть основное различие в характере работ — оно определяет и объём, и профиль рисков, но не отвечает за долгосрочные потребности проекта, где перевес у Next.

Сценарий повторного рефакторинга через 6–12 месяцев

Факторы, которые могут потребовать пересмотра архитектурного решения — вне зависимости от того, какой фреймворк выбран сейчас.

Изменение бизнес-требований

Если продукт выйдет за пределы внутренней ERP-системы и появится потребность в SEO-оптимизированных публичных страницах, потребуется более глубокая интеграция с SSR и статической генерацией. Это может стать аргументом в пользу Next.js, который имеет зрелые инструменты для таких сценариев.

Эволюция экосистемы

Если TanStack Start не успеет за развитием React — например, если RSC станет доминирующей парадигмой и потребуется глубокая поддержка — команда может столкнуться с необходимостью миграции на фреймворк с более зрелой RSC-реализацией. В то же время, если Next.js продолжит усложняться (новые версии App Router с кардинальными изменениями), поддержка существующего кода может потребовать больше усилий, чем ожидалось.

Рост команды или изменение её состава

Если в проект придут разработчики с опытом работы с одним из фреймворков, это может повлиять на выбор в пользу более знакомого стека. Однако при грамотном документировании и наличии чётких архитектурных принципов этот фактор менее критичен.

Технические ограничения

Если выяснится, что выбранный фреймворк не справляется с нагрузкой — например, время ответа SSR превышает допустимые значения, — может потребоваться пересмотр подхода. Это может быть как проблема конкретной реализации, так и архитектурное ограничение фреймворка.

Главный вывод

Любой выбор несёт риск, что через полгода потребуется корректировка. Однако при условии, что оба плана миграции предполагают поэтапное внедрение и наличие плана отката, команда сможет адаптироваться к изменениям с минимальными потерями. Ключевой фактор — не столько сам фреймворк, сколько качество документации, модульность кода и наличие системы автоматического тестирования, которую предстоит создать.

Подходы к тестированию

Здесь планы совпадают почти полностью — и это самая уязвимая часть обоих.

Next.js — план тестирования

Ручной чек-лист на 200+ сценариев, разбитый на 13 блоков по доменным модулям. Эталонные скриншоты и печатные формы снимаются на этапе 0, до начала изменений, и сравниваются после. Сверху — опциональный Playwright-смоук на критические пути.

Зона проверки шире: переписан роутинг, поэтому в объём регресса попадают все 132 маршрута плюс поведение хлебных крошек и типизация ссылок.

TanStack Start — план тестирования

Тот же подход: ручной чек-лист на 272 сценария по тем же 13 блокам, эталонные артефакты этапа 0, параллельная эксплуатация две недели, опциональный Playwright-смоук.

Отдельные сценарии (SEC-06, SEC-15) проверяют отказ в доступе через curl, а не через поведение интерфейса: при выключенном SSR beforeLoad выполняется в браузере и серверной защитой не является.

Общее ограничение обоих планов

В проекте 0 автотестов при настроенном Vitest. Ни один из планов это не меняет: оба опираются на ручной прогон и опциональный смоук. Это означает, что качество приёмки целиком зависит от дисциплины прохождения чек-листа. Последствия пропущенной ошибки одинаковы в обоих вариантах — различается только объём затронутого кода, то есть вероятность, что ошибка вообще возникнет.

Стратегии отката

Что можно откатить, на каком уровне и за какое время — если после выкатки что-то пойдёт не так.

Next.js

Уровень 1 — полный откат на статику. Vite-сборка остаётся на сервере и продолжает собираться в CI минимум 4 недели после переключения. Переключение — один подключаемый файл nginx, менее двух минут.

Частичный откат возможен только через маршрутизацию в nginx: часть путей уходит на Next, часть — на старую сборку. Это работает, но требует ручного ведения списка путей и разъезжается с сессиями.

Отката «внутри фреймворка» нет: чтобы вернуть страницу к клиентскому рендеру, её нужно конвертировать обратно из Server Component в Client Component.

TanStack Start

Уровень 1 — точечный отказ от SSR. Проблемный маршрут возвращается к клиентскому рендеру одной строкой: ssr: false в его определении. Остальное приложение не затрагивается.

Уровень 2 — глобальный откат SSR. defaultSsr: false возвращает всё приложение в SPA-режим на Node. Серверные функции, httpOnly-сессия и прокси секретов при этом продолжают работать — цель миграции не теряется.

Уровень 3 — полный откат на статику. Тот же механизм, что у Next: подключаемый файл nginx и сохранённая Vite-сборка.

Как пользоваться этим сравнением

Оба плана достигают заявленной цели — httpOnly-сессия, секреты на сервере, серверная защита маршрутов — и в обоих она достигается к концу этапа 4. Дальше расхождение определяется не самой целью, а тем, что важнее в конкретный момент.

Взвешенная оценка даёт 7.7 у TanStack Start и 6.4 у Next.js, но она построена на весах, отражающих приоритеты этого проекта сегодня: тройной вес у сложности миграции и безопасности, двойной — у долгосрочной перспективы. Если поднять вес долгосрочной перспективы и производительности, соотношение меняется в пользу Next.js. Выбор зависит от приоритетов команды и бизнес-требований.
